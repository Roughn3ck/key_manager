# ColdStack v5.1.4 — gui_main_v5.py Carve-Off

**Author:** Slater (CTO)
**Date:** 2026-07-27
**Status:** PROPOSED — awaiting Kris's approval

---

## The Problem

`gui_main_v5.py` is 6,424 lines. It contains 4 major sections that are self-contained enough to extract into independent modules. The v5.1.x pattern already established this discipline with `swap_dialog.py`, `lp_liquidity_manager.py`, `evm_transfer_dialog.py`, and `vault_deposit_dialog.py`.

## What Can Be Carved Off

| Section | Lines | Extract To | Self-Contained? |
|---------|-------|------------|-----------------|
| LP tab (create_lp_tab + all `_lp_*` methods) | ~1,825 | `lp_tab.py` | ✅ Yes — all LP logic is prefixed `_lp_` |
| Vault section (create_vault_section + all `_vault_*` methods) | ~847 | `vault_tab.py` | ✅ Yes — all vault logic is prefixed `_vault_` |
| Dialogs (add account, add address, add mnemonic, add PK, derivation, import, init vault, change password) | ~880 | `account_dialogs.py` | ✅ Yes — all are dialog methods |
| Settings dialog | ~281 | `settings_dialog.py` | ✅ Yes — self-contained dialog |

**Total carve-off: ~3,833 lines**
**gui_main_v5.py after: ~2,591 lines** (6,424 - 3,833)

## What Stays in gui_main_v5.py

| Section | Lines | Why it stays |
|---------|-------|-------------|
| Imports + globals + ssl fix | ~157 | App-level setup |
| PortableKeyManager class | ~156 | Core vault manager — tightly coupled to GUI |
| ColdStackGUI.__init__ | ~60 | Main window setup |

| Update check | ~86 | App-level concern |

| Private key section | ~196 | Core wallet view |

| run() | ~7 | Entry point |

**~2,591 lines remaining** — this is the core wallet GUI. Everything that was a "feature tab" or a "dialog" gets carved off.

## Extraction Order (Least Risky First)

### Extraction 1: Settings Dialog → `settings_dialog.py`
- **Lines carved:** ~281
- **Risk:** Low — it's a self-contained dialog with minimal coupling
- **Pattern:** Same as swap_dialog.py — the dialog takes the GUI instance (or specific callbacks) and builds itself

### Extraction 2: Account Dialogs → `account_dialogs.py`
- **Lines carved:** ~880
- **Risk:** Low-Medium — dialogs are self-contained, but some reference `self._get_all_account_names()` and balance engine
- **Pattern:** Module-level functions that take `gui` instance + callbacks. Same as lp_liquidity_manager.py pattern

### Extraction 3: Vault Section → `vault_tab.py`
- **Lines carved:** ~847
- **Risk:** Medium — vault section has its own state management (`_vault_*` methods)
- **Pattern:** A `VaultTab` class that takes the GUI instance. Similar to how vault_tracker.py and vault_deposit_dialog.py already work

### Extraction 4: LP Tab → `lp_tab.py`
- **Lines carved:** ~1,825
- **Risk:** Medium-High — largest section, has fetch threads, card rendering, fee/compound/close dialogs
- **Pattern:** An `LPTab` class that takes the GUI instance. The existing `lp_liquidity_manager.py` already handles add/remove/edit — this extracts the rest (tab setup, fetch/scan, card rendering, pool save/remove, fee/compound/close dialogs)
- **Note:** Some LP methods call `lp_liquidity_manager` functions (already extracted). The new `lp_tab.py` would import from `lp_liquidity_manager.py`.
